# 作業の流れ

## 1. やることを決める — GitHub Issues

- やりたいこと・直したいことは Issue にする
- 自分が手を付けるときは **Assignees に自分を入れる**（＝「触るな」の合図。同じところを二人で直すのを防ぐ）
- 小さく切る。1つの Issue は1〜2日で終わる大きさ

## 2. 直す — ブランチ

```sh
git switch main && git pull
git switch -c fix/投稿画面の文言    # feat/… fix/… chore/… docs/…
# 直す
npm run build                       # 通ることを確かめる
git add -A && git commit -m "fix(post): 投稿画面の文言を直す"
git push -u origin HEAD
```

コミットメッセージは `種類(場所): 何をしたか` を日本語で（`git log` を見ると例がたくさんある）。

## 3. 見てもらう — PR

- GitHub で PR を作る。テンプレートに沿って「何を・なぜ・どう確かめたか」を書く
- PR にプレビュー URL が自動で付く。**スマホで触って確かめてから**レビューを頼む
- 必要に応じてラベルを付ける
  - `needs:prod-sql` … 本番の DB に SQL を流す必要がある
  - `needs:env` … 本番の環境変数を足す・変える必要がある
  - `needs:merge` … 確認が終わってマージ待ち

## 4. 本番に出す — 柴野

マージと本番デプロイ（`vercel --prod`）、本番の SQL は柴野がまとめてやる。
Android には本番デプロイの時点で届く。iOS には次のアプリ更新（審査）で届く。

## LP（ランディングページ）

アプリとは別のプロジェクトにして `fanhive.jp` の下のパスで出す予定。
LP は壊れてもアプリに影響しないので、LP だけの PR はメンバーがマージしてよい（作ったらここに追記する）。
